## Subsequent user startup: Discord command diagnosis

Later the same evening, after the user installed dependencies and started PM2,
read-only checks found Node 24.22.1 running the deployed bot with the intended
loopback HTTP listener. Discord logged Ready, but PM2 repeatedly restarted the
process about every 30 seconds. Its own log explicitly attributes these restarts
to the saved 160 MiB memory threshold; observed usage at those checks was about
163–168 MiB. Watch mode was off. This is a process-manager restart, not a
reported application exception or evidence that the proxy blocks Discord.

MongoDB was still inactive. A read-only ping using the configured MongoDB URL
failed with MongoServerSelectionError after a three-second selection timeout;
the URL targets loopback. The slash handler awaits a guild database write before
running the command's response logic, so an unavailable database can consume
Discord's initial-response deadline even when login succeeds.

No services, PM2 settings or bot code were changed by the agent during diagnosis.
The user subsequently confirmed MongoDB was the command failure's cause.

## Web API diagnosis and final wrap-up

The browser subsequently reported CORS errors for `/api/me`. Both the public
HTTPS URL and the direct loopback upstream returned Express 404 without CORS
headers. `WEB_BATTLER_ENABLED` was unset, so neither `/api` nor its CORS
middleware was mounted. The allowed origin and callback were already correct.
Enabling the flag and restarting was the prescribed fix, without relaxing CORS.

The user then reported everything working. Fresh read-only wrap-up checks found:

User-reported success covers the user's own live flow; it is not evidence that
every mode, physical device, provider, restart or partial-reward case was run.
No production configuration was changed during this documentation wrap-up.
